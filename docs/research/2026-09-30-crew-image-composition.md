# Crew image composition from independently versioned layers

Research for [#2268](https://github.com/flotilla-org/flotilla/issues/2268), the wayfinder for [#2267](https://github.com/flotilla-org/flotilla/issues/2267). This compares construction methods; it does not propose a resource schema or change the fleet image baseline.

## Current boundary

The current [Dockerfile](../../.flotilla/Dockerfile.crew) has Ubuntu and network clients, language toolchains (Rust, Node, Zig), forge tools, then Claude Code and Codex in its final stage. The separate Ghostty builder contributes terminfo near the end. Version arguments for the adapters occur immediately before their installation, so changing only `CODEX_VERSION` can reuse earlier cached steps. The [Forgejo workflow](../../.forgejo/workflows/crew-image.yml) nevertheless runs a full two-platform `buildx build --push`, then pulls and checks the published image on the runner's native platform. Its tag includes the commit and a hash of the five version inputs. That hash distinguishes invocations; it is not the OCI image digest or a complete content key (the Ubuntu tag, apt repositories, npm packages, download endpoints, build implementation, and compression can change independently).

The relevant distinction is **re-executing a build step** versus **uploading a layer**. A cache miss can cause a costly reinstall. A changed final image manifest does not by itself require uploading unchanged blobs. Registry push can reuse blobs already present; the OCI distribution API also permits mounting a blob from another repository in the same registry, with an upload fallback when the mount cannot be made ([OCI distribution specification](https://github.com/opencontainers/distribution-spec/blob/main/spec.md#mounting-a-blob-from-another-repository)). Cache availability and registry blob availability are separate.

## Comparison

“Adapter bump” means changing Codex while keeping the toolchain and other inputs fixed. “Local” means the host has no image registry; a Docker daemon may still exist. Every option can emit only `linux/amd64` or only `linux/arm64`, subject to source artifacts existing for that platform.

## Tradeoffs that matter here

### Dockerfile fragments and chained images

Generated fragments solve ownership and authoring: base, harness, capability, and project can each publish a fragment and version it. Generation must produce a stable instruction order and record exact inputs. It does **not** make those pieces independently addressable as image objects. In the current Dockerfile a Codex bump already leaves earlier toolchain steps eligible for cache hits because the argument appears late; this is the cheapest path if the problem is simply routine adapter updates. It still relies on an available build cache to avoid reinstalling toolchains ([Docker cache invalidation](https://docs.docker.com/build/cache/invalidation/)).

Chained images turn boundaries into published OCI images. A capability recipe can say `FROM harness@sha256:…`; a project recipe can say `FROM capability@sha256:…`. This makes independently pinned parents inspectable and reusable, and a host with those images can build locally with ordinary Docker. It also makes the dependency graph explicit: updating a lower parent changes the input to every child. Re-running a descendant `RUN` after such an update may be necessary because it could have observed the parent's filesystem. Docker cannot generally infer that the child action is independent. If a child only deposits files, BuildKit's `COPY --link` can retain that layer and allow a rebase without reading the old base ([Dockerfile reference](https://docs.docker.com/reference/dockerfile/#copy---link)); this does not cover `apt`, `npm install`, or smoke tests that execute programs in the parent.

### OCI append and metadata

The OCI image manifest lists layer descriptors and a separate config blob; the config owns environment variables, entrypoint, user, working directory, history, and uncompressed layer DiffIDs. A filesystem layer alone cannot declare all the adapter behavior. An append implementation must construct a valid new config and manifest, preserve platform identity, and decide how whiteouts, file ownership, and paths interact with lower layers ([OCI image manifest](https://github.com/opencontainers/image-spec/blob/main/manifest.md), [OCI image config](https://github.com/opencontainers/image-spec/blob/main/config.md), [OCI layer format](https://github.com/opencontainers/image-spec/blob/main/layer.md)).

`crane append` adds tar contents to an optional base and can write a tar output; `crane mutate` additionally exposes config edits such as env, command, user, and workdir ([append command](https://github.com/google/go-containerregistry/blob/main/cmd/crane/doc/crane_append.md), [mutate command](https://github.com/google/go-containerregistry/blob/main/cmd/crane/doc/crane_mutate.md)). `umoci` works on local OCI image layouts and can repack a modified root filesystem ([umoci documentation](https://umo.ci/)). These are attractive for a prebuilt, relocatable file tree. The present adapters are installed with `npm install --global` against the Node installation in the parent, while the Dockerfile also runs executable checks and contributes Ghostty terminfo; packaging those outputs into correct standalone layers, preserving symlinks/permissions and platform, and running the checks elsewhere is real new work. An arbitrary layer rebase can create a broken image even when the manifest is structurally valid ([crane rebase caveats](https://github.com/google/go-containerregistry/blob/main/cmd/crane/rebase.md)).

Multi-platform publication still requires one valid image per platform plus an image index pointing at each; an OCI layer is not architecture-agnostic merely because it is a tarball ([OCI image index](https://github.com/opencontainers/image-spec/blob/main/image-index.md)). The current Dockerfile downloads architecture-specific Node, Zig, and tea artifacts, so native-only builds are possible but must use the matching artifacts. A registry-less Docker host can receive an image tar and `docker load` it; a local OCI layout may require a conversion/import tool. Distribution between registry-less hosts is then file transfer or a separate content store, not automatic cache sharing.

### BuildKit and Nix

Buildx Bake is a declarative build invocation planner, not a new image format. It is useful for enumerating layer/version/platform targets and producing a consistent plan, but it does not independently cache a changed `RUN` instruction ([Bake reference](https://docs.docker.com/build/bake/reference/)). Direct LLB offers precise graph construction at the cost of maintaining a custom frontend or generator. `COPY --link` is a narrower, documented rebase mechanism that could help if adapters become installable as prebuilt trees ([Dockerfile reference](https://docs.docker.com/reference/dockerfile/#copy---link)). BuildKit's registry cache can export intermediate layers even when they are not in the final image; its local backend covers a host without a registry ([cache backends](https://docs.docker.com/build/cache/backends/), [registry cache](https://docs.docker.com/build/cache/backends/registry/)).

Nix offers a stronger input-addressed build graph and cross-host binary cache. `dockerTools.buildLayeredImage` partitions store paths into layers; nix2container can define explicit stable layers and copy to a registry or Docker daemon ([Nixpkgs manual](https://nixos.org/manual/nixpkgs/stable/), [nix2container README](https://github.com/nlewo/nix2container)). For this image it means replacing or wrapping apt, rustup, npm, curl-based archives, the pinned cleat checkout, and smoke checks as Nix derivations. That is a migration of the toolchain supply chain, not just an image-layer change. Nix store paths can tell us whether a derivation's inputs changed, but the registry digest remains a hash of the finished OCI bytes.

## Identity and skip policy

Use two identities. A **recipe key** can be computed before build from the pinned source revisions, exact parent image digest, adapter versions and integrity pins, target platform, Dockerfile/fragments, builder/tool version, and relevant build options. Query an artifact index or registry tag derived from that key; if present, verify its manifest/platform and reuse its recorded digest. The **OCI digest** is computed from the emitted manifest bytes and identifies the artifact actually run. Do not treat the current eight-character workflow input hash as either a complete key or a content digest. Because apt repositories and npm install resolution are presently mutable inputs, identical declared version strings alone do not guarantee identical results ([OCI descriptor digests](https://github.com/opencontainers/image-spec/blob/main/descriptor.md), [BuildKit reproducibility controls](https://github.com/moby/buildkit/blob/master/docs/build-repro.md)). Pin or capture those external artifacts to make the recipe key trustworthy.

## Recommendation for #2267

Start with **digest-pinned chained images at coarse boundaries**, while retaining Dockerfiles and the current BuildKit/buildx publisher: (1) slow base/toolchains, (2) forge and utility tools, (3) harness adapters, then (4) optional project additions. Publish each platform's parent digest and an index for the chosen final image. A routine Codex bump starts from the pinned toolchain/utility image and changes only the harness build and its checks; no toolchain build is needed, and a registry push can reuse its blobs. If project additions have `RUN` steps, expect to rerun them after a harness-parent change; move independent file-only additions to `COPY --link` when that dependency is proven. This is a deliberate boundary choice, not a guarantee that every descendant command can be skipped.

Keep a generated Dockerfile/Bake file as an *authoring interface* only if independent producers need it. Use BuildKit's registry cache for the persistent fleet and local cache export for a registry-less builder. Keep native-platform builds available, while the central workflow continues to publish both architectures and check the finished image. Record the recipe key and final digest separately and retain the current runtime smoke checks. A later spike can test OCI append for a single relocatable adapter artifact; do not make append the general installer until it can preserve OCI config, architecture, and the current checks. Nix is credible if the project later wants Nix-controlled toolchains across hosts, but is disproportionate solely to avoid rebuilding the late npm layer.

The Docker approaches require access to a Docker daemon, which commonly means a privileged daemon or permission to its socket; the CLI does not itself require UID 0. BuildKit has a documented [rootless mode](https://github.com/moby/buildkit/blob/master/docs/rootless.md) with host prerequisites. `crane` and local OCI-layout tooling can compose without a daemon or root, and Nix can produce an image artifact without Docker; a Docker host still needs daemon access to load and run that artifact. A single host can use native-platform images and its local cache without a registry. Sharing layers across registry-less hosts requires transferring an image, OCI layout, BuildKit local cache, or Nix store closure by another channel.

BuildKit registry cache export should use `mode=max` if reuse of intermediate build stages matters; the default `mode=min` exports layers from the final result only ([cache mode reference](https://docs.docker.com/build/cache/backends/#cache-mode)). If the publisher emits provenance or SBOM attestations, those bind to the final image/index digest and must be regenerated for a newly composed result; Buildx's default provenance and opt-in SBOM behavior are documented in [Docker build attestations](https://docs.docker.com/build/metadata/attestations/). This is an additional reason to keep a single publisher responsible for the final digest.

## Local verification and limits

This vessel has no Docker, Podman, Buildah, Skopeo, or local registry, so no real crew image was built. I downloaded `crane` v0.22.1 from its [official release](https://github.com/google/go-containerregistry/releases/tag/v0.22.1) through the injected authenticated GitHub CLI, outside the checkout. I made a tiny tar layer with fixed tar ordering, owner, and mtime, then ran `crane append --new_layer layer.tar --new_tag example.invalid/demo:fixed --output output.tar` twice. `crane digest --tarball` reported the same digest both times, `sha256:cfeb0f04ced6c24ef99f3f843b24a99bdfbc35341db381c85dfdbd26262f02aa`. Changing the file contents changed the digest to `sha256:8f1c1fb81dc00c3df489c6a14dca4379492f04b9de4cf61552a15e0e7615261d`. This verifies offline tar output and byte-stable repetition for that pinned tool and normalized input. It does **not** verify append onto a real base, registry deduplication, multi-platform output, Docker loading, or the current npm-installed adapters. The empty-base output's config had blank OS and architecture, so it is not a runnable crew-image example. All other tool behavior above comes from the linked first-party documentation; applicability and recommendation are reasoned from that documentation and the checked-in files.
