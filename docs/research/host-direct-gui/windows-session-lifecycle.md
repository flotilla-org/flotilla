# Windows host-direct GUI session and authentication lifecycle

Research for [flotilla-org/flotilla#1998](https://github.com/flotilla-org/flotilla/issues/1998), 2026-09-25. This is an OS mechanism assessment, not a claim that the path has been tested on beaufort.

## Finding

An SSH command arriving in a service context cannot make its own windows visible in the user's desktop. Windows runs services in Session 0 and, since Vista, services cannot directly interact with a user. The supported pattern is a separate process in an **existing logged-on user's session**, launched by a user-session task or by a trusted service using that user's token, with IPC back to the service. The GUI process must use the interactive `winsta0\default` desktop. [Microsoft: Interactive Services](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services), [Window Station and Desktop Creation](https://learn.microsoft.com/en-us/windows/win32/winstation/window-station-and-desktop-creation), [CreateProcessAsUserW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessasuserw).

This crosses a **process/session boundary**, not an authentication boundary: a user must already be logged on, or an authorized component must arrange a real logon. A task with `InteractiveToken` runs only in an existing interactive session; an S4U task has no stored password but does not provide an interactive logon or network access. `WTSQueryUserToken` obtains the logged-on user's primary token for a specified session, and its caller must be LocalSystem with `SeTcbPrivilege`; it cannot manufacture a user session at the sign-in screen. [Task Scheduler LogonType](https://learn.microsoft.com/en-us/windows/win32/taskschd/taskschedulerschema-logontype-principaltype-element), [WTSQueryUserToken](https://learn.microsoft.com/en-us/windows/win32/api/wtsapi32/nf-wtsapi32-wtsqueryusertoken).

## Launch choices

| Mechanism | What it provides | Limitation / authority |
| --- | --- | --- |
| Interactive scheduled task | Register an `ONLOGON` task for the dedicated GUI account with `/IT`; the user-session helper starts at logon and receives work over a restricted local IPC channel. `schtasks /run` can invoke the registered task on demand. | `/IT` requires that `/RU` is already logged on; it does not log the user in. Task registration and the user logon are setup/operational prerequisites. [schtasks create](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/schtasks-create), [schtasks](https://learn.microsoft.com/en-us/windows/win32/taskschd/schtasks), [Task Scheduler LogonType](https://learn.microsoft.com/en-us/windows/win32/taskschd/taskschedulerschema-logontype-principaltype-element). |
| LocalSystem service launcher | Enumerate/select a session, call `WTSQueryUserToken(session_id)`, then `CreateProcessAsUserW` with `STARTUPINFO.lpDesktop = L"winsta0\\default"`; keep the trusted service and user GUI helper separate. | Requires a privileged, installed service and careful token/IPC handling. `CreateProcessAsUserW` generally needs `SeIncreaseQuotaPrivilege`, sometimes `SeAssignPrimaryTokenPrivilege`; the desktop/window-station DACL must admit the token. Close token handles. [Interactive Services](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services), [WTSQueryUserToken](https://learn.microsoft.com/en-us/windows/win32/api/wtsapi32/nf-wtsapi32-wtsqueryusertoken), [CreateProcessAsUserW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessasuserw). |
| User logon startup helper | Install a per-user startup entry that runs inside each logon session; the Session-0 side only contacts the appropriate helper. | Requires a user logon; the helper and IPC must identify the right session/user. Microsoft describes the service/helper pattern and `Run` startup for multiuser systems. [Interactive Services](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services). |

The ordinary SSH account does not acquire `WTSQueryUserToken` authority merely by being an administrator: that API requires a LocalSystem caller with `SeTcbPrivilege`. An SSH command can request work from a preinstalled broker or run an authorized interactive task; treating an arbitrary remote command as the privileged launcher would erase the intended authority boundary. [WTSQueryUserToken](https://learn.microsoft.com/en-us/windows/win32/api/wtsapi32/nf-wtsapi32-wtsqueryusertoken), [Interactive Services](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services).

The service should identify a **specific** account and session, not assume the physical console is the only target. `WTSGetActiveConsoleSessionId` identifies the session attached to the physical console and can return `0xFFFFFFFF` during attach/detach. `WTSEnumerateSessions` and `WTS_CONNECTSTATE_CLASS` distinguish active and disconnected RDP sessions; `quser` exposes user, session ID, and state for diagnosis. A service can subscribe to `WM_WTSSESSION_CHANGE` (logon, logoff, lock, unlock, remote connect/disconnect) and re-evaluate its helper when the session changes. [WTSGetActiveConsoleSessionId](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-wtsgetactiveconsolesessionid), [WTSEnumerateSessionsW](https://learn.microsoft.com/en-us/windows/win32/api/wtsapi32/nf-wtsapi32-wtsenumeratesessionsw), [WTS_CONNECTSTATE_CLASS](https://learn.microsoft.com/en-us/windows/win32/api/wtsapi32/ne-wtsapi32-wts_connectstate_class), [quser](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/quser), [WM_WTSSESSION_CHANGE](https://learn.microsoft.com/en-us/windows/win32/termserv/wm-wtssession-change).

For the service route, `CreateProcessAsUserW` does not automatically load the user's profile or build the right environment. Use `LoadUserProfileW` where required and `CreateEnvironmentBlock`, passing the block with `CREATE_UNICODE_ENVIRONMENT`; set an explicit executable path, working directory, and desktop. This is implementation guidance derived from the API contracts, not a tested command for beaufort. [CreateProcessAsUserW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessasuserw), [CreateEnvironmentBlock](https://learn.microsoft.com/en-us/windows/win32/api/userenv/nf-userenv-createenvironmentblock), [LoadUserProfileW](https://learn.microsoft.com/en-us/windows/win32/api/userenv/nf-userenv-loaduserprofilew).

## Logon, reboot, lock, and RDP

**Reboot:** A Windows user session does not persist through reboot. To recreate a console GUI session without a person, an administrator can configure Windows AutoAdminLogon for a dedicated account, then use the logon-triggered helper/task. Microsoft's Sysinternals Autologon stores credentials as an LSA secret rather than the plain-text Winlogon `DefaultPassword`, but an administrator can recover them; physical access and credential rotation therefore matter. Autologon can fail if credentials are invalid, logon rights/policies block the account, an interactive logon banner is configured, or other documented policy conditions apply. This is one-time human/admin setup followed by conditional unattended renewal, not a guarantee of permanent access. [Autologon](https://learn.microsoft.com/en-us/sysinternals/downloads/autologon), [Configure automatic logon](https://learn.microsoft.com/en-us/troubleshoot/windows-server/user-profiles-and-logon/turn-on-automatic-logon).

Windows' *Automatic Restart Sign-On* is a different feature: after certain system/update restarts it signs in the last interactive user **and locks the session**. It is not a general replacement for configured autologon when visual GUI driving is required. [Winlogon ARSO](https://learn.microsoft.com/en-us/windows-server/security/windows-authentication/winlogon-automatic-restart-sign-on-arso).

| Event | Renewal condition for a visual crew |
| --- | --- |
| SSH connection or helper process restarts | Reconnect to the helper or rerun the interactive task **only while the chosen user session still exists**; neither operation signs a user in. [Task Scheduler LogonType](https://learn.microsoft.com/en-us/windows/win32/taskschd/taskschedulerschema-logontype-principaltype-element). |
| User signs out or Windows reboots | A new interactive logon is required. A person can sign in, or configured autologon can attempt a console sign-in at boot; the logon trigger then starts a new helper. [Autologon](https://learn.microsoft.com/en-us/sysinternals/downloads/autologon), [schtasks create](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/schtasks-create). |
| Stored autologon password becomes invalid or policy requires a password change | The stored credential or policy condition must be repaired by an authorized operator before automatic sign-in can resume. ARSO also documents password-change-at-next-logon as a failure condition. [Configure automatic logon](https://learn.microsoft.com/en-us/troubleshoot/windows-server/user-profiles-and-logon/turn-on-automatic-logon), [Winlogon ARSO](https://learn.microsoft.com/en-us/windows-server/security/windows-authentication/winlogon-automatic-restart-sign-on-arso). |
| Session locks or RDP disconnects | The user's process may remain alive, but visual input/capture must pause until the application desktop is again usable and the capture interface is recreated as needed. Restoring that state can require an authenticated person or an explicitly provisioned session policy; a token launcher does not unlock it. [Desktops](https://learn.microsoft.com/en-us/windows/win32/winstation/desktops), [IDXGIOutput1::DuplicateOutput](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgioutput1-duplicateoutput). |

**Lock/UAC:** `winsta0` has distinct Default and Winlogon desktops; only one is the input desktop at a time. The locked state displays a secure desktop until credentials unlock it. A GUI helper may still exist on Default, but its visible pixels and injected input are not the active locked desktop. No task, `CreateProcessAsUserW` call, or Session-0 privilege is an authenticated unlock operation. [Desktops](https://learn.microsoft.com/en-us/windows/win32/winstation/desktops), [Winlogon States](https://learn.microsoft.com/en-us/windows/win32/secauthn/winlogon-states), [Task Scheduler LogonType](https://learn.microsoft.com/en-us/windows/win32/taskschd/taskschedulerschema-logontype-principaltype-element).

**RDP:** A person using RDP may create or reconnect to a session different from the console session, and disconnect can leave the user signed in but the session disconnected. Treat Robert's current RDP use as a session ownership/state transition: enumerate the actual target session before launching or capturing. `tscon` can connect one session to another subject to Connect/Full Control permission and the target user's password if different, but Microsoft's command reference says it cannot connect *to* the console session; do not assume a scripted `tscon ... /dest:console` is a supported recovery contract without beaufort testing. [WTS_CONNECTSTATE_CLASS](https://learn.microsoft.com/en-us/windows/win32/api/wtsapi32/ne-wtsapi32-wts_connectstate_class), [quser](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/quser), [tscon](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/tscon).

An RDP client being **minimized** can also affect screen-oriented automation even while its session remains connected; Microsoft lists it separately from lock and UAC failures in Power Automate. Validate the exact RDP client and capture stack on beaufort instead of treating a successful token launch as proof that frames and input will work. [Power Automate UIPI troubleshooting](https://learn.microsoft.com/en-us/troubleshoot/power-platform/power-automate/desktop-flows/ui-automation/uipi-issues).

## GUI driving and porthole capture

`SendInput` injects keyboard/mouse events and is limited by User Interface Privilege Isolation: it can target equal or lower integrity processes. The active input desktop also matters; a locked workstation or UAC secure desktop is not the app's Default desktop. Microsoft's `winapp ui` documentation explicitly separates input-injecting verbs, which require an unlocked interactive desktop, from UI Automation pattern operations such as inspect, set-value, and invoke, which can work in a locked session. Thus **some semantic UIA operations can continue while locked**, but a visual porthole workflow requiring screenshots and physical-style clicks must require a usable, unlocked target desktop and application-specific validation. [SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput), [Desktops](https://learn.microsoft.com/en-us/windows/win32/winstation/desktops), [winapp UI Automation](https://learn.microsoft.com/en-us/windows/apps/dev-tools/winapp-cli/ui-automation), [Power Automate UIPI troubleshooting](https://learn.microsoft.com/en-us/troubleshoot/power-platform/power-automate/desktop-flows/ui-automation/uipi-issues).

For DXGI desktop duplication, `DuplicateOutput` returns `E_ACCESSDENIED` without privilege to the current desktop image (only LocalSystem can access the secure desktop) and `DXGI_ERROR_SESSION_DISCONNECTED` for a disconnected session. A desktop switch or display-mode change invalidates existing duplication interfaces, which must be recreated. This makes lock/unlock and RDP transitions explicit capture lifecycle events; service privilege is not a way to provide the normal user's app desktop to an SSH process. Microsoft's `winapp` screenshot command likewise warns that capture can need an interactive desktop. [IDXGIOutput1::DuplicateOutput](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgioutput1-duplicateoutput), [IDXGIOutputDuplication](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nn-dxgi1_2-idxgioutputduplication), [winapp UI Automation](https://learn.microsoft.com/en-us/windows/apps/dev-tools/winapp-cli/ui-automation).

Existing porthole integration has an independent transport boundary: the ordinary HTTP control endpoint can use a Windows named pipe, but the capture-transfer socket is currently disabled on Windows and Unix capture handoff uses file descriptors/shared memory. Getting a GUI process into the right Windows session does **not** by itself make porthole capture available remotely; Windows capture and its data path need separate application work. [Porthole transport source](https://github.com/flotilla-org/porthole/blob/80077606c23042512eaa8fc6c5492efb30cf84a7/crates/porthole-transport/src/lib.rs), [portholed server source](https://github.com/flotilla-org/porthole/blob/80077606c23042512eaa8fc6c5492efb30cf84a7/crates/portholed/src/server.rs), [capture registry source](https://github.com/flotilla-org/porthole/blob/80077606c23042512eaa8fc6c5492efb30cf84a7/crates/portholed/src/capture_registry.rs).

## Suggested beaufort validation and operator commands

The commands below are **examples to run on Windows after the dedicated account and executable paths are chosen**. They do not authenticate a user or assert that beaufort is already configured. Microsoft documents the `/IT`, `/RU`, `/SC ONLOGON`, `/RUN`, and query behavior. [schtasks create](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/schtasks-create), [schtasks](https://learn.microsoft.com/en-us/windows/win32/taskschd/schtasks), [quser](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/quser).

```cmd
quser
query session
schtasks /create /tn "FlotillaGuiHelper" /tr "C:\Path\To\gui-helper.exe" /sc onlogon /ru "BEAUFORT\GuiUser" /it
schtasks /query /tn "FlotillaGuiHelper" /v /fo list
schtasks /run /tn "FlotillaGuiHelper"
```

Verify the helper's PID/session ID, user token, `winsta0\default` desktop, IPC access, application launch, real input, and actual porthole capture while the session is unlocked. Then repeat after lock/unlock, RDP connect/disconnect/reconnect, sign-out/sign-in, and reboot. Expect a fresh user session and helper after sign-in; pause visual work when locked or disconnected; recreate capture after desktop switches; require a person or explicitly authorized autologon to restore the interactive state. These are proposed acceptance checks derived from Microsoft's session, desktop, input, and capture contracts. [WM_WTSSESSION_CHANGE](https://learn.microsoft.com/en-us/windows/win32/termserv/wm-wtssession-change), [Desktops](https://learn.microsoft.com/en-us/windows/win32/winstation/desktops), [SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput), [IDXGIOutputDuplication](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nn-dxgi1_2-idxgioutputduplication).

**Unattended after setup:** SSH can ask an already-running user helper to operate; a registered interactive task can restart it at a subsequent logon; a trusted LocalSystem service can launch it into an existing user's session; configured autologon can recreate a console logon after reboot under its documented conditions. **Human/admin setup or intervention:** install/register the helper or service and its IPC permissions, choose the dedicated account and credential handling, provision autologon if acceptable, perform the initial logon or unlock when autologon is absent, and recover from blocked logon, sign-out, lock, or disconnected RDP when no supported automated sign-in path exists. This division follows the cited Task Scheduler, token, autologon, and desktop contracts. [Task Scheduler LogonType](https://learn.microsoft.com/en-us/windows/win32/taskschd/taskschedulerschema-logontype-principaltype-element), [WTSQueryUserToken](https://learn.microsoft.com/en-us/windows/win32/api/wtsapi32/nf-wtsapi32-wtsqueryusertoken), [Autologon](https://learn.microsoft.com/en-us/sysinternals/downloads/autologon), [Winlogon States](https://learn.microsoft.com/en-us/windows/win32/secauthn/winlogon-states).
