# Linux host-direct graphical seat: session and authorization lifecycle

Research for [#1999](https://github.com/flotilla-org/flotilla/issues/1999), 2026-09-25. This describes a process reached over SSH on the *target host* that must launch, capture, and control an app on that host's physical graphical desktop. The actual display manager, compositor, login policy, and installed portal backend on `paneer` have not been verified; the commands below are discovery steps, not observations about that machine.

## Findings

An SSH shell is a separate remote login session. It does not inherit the physical desktop's `DISPLAY`, `WAYLAND_DISPLAY`, `XAUTHORITY`, or compositor state. `ssh -X`/`-Y` sets a *proxy* `DISPLAY` on the target that renders back to the SSH **client**, so it is the wrong display for host-direct capture. Avoid X forwarding for this path and select the target host's local graphical session explicitly. [OpenSSH `ssh(1)`, X11 forwarding](https://man.openbsd.org/ssh.1#X11_FORWARDING); [logind session model](https://wiki.freedesktop.org/www/Software/systemd/logind/).

`logind` distinguishes local seat sessions from remote sessions with `Seat`, `Remote`, `Type`, `Class`, and `Active` properties. `Display` is an X11 display field; it is not a Wayland socket locator. A display manager's greeter may itself be a `greeter` class graphical session, but it is not the intended user's authenticated desktop. Select an `Active=yes`, `Remote=no`, `Class=user`, `Type=x11|wayland` session on the intended seat and owned by the intended UID; fail closed if no unique match exists. Merely knowing a UID or seeing `/run/user/$UID` does not prove that a usable graphical session exists. [logind D-Bus interface and property definitions](https://wiki.freedesktop.org/www/Software/systemd/logind/); [`loginctl(1)`](https://www.freedesktop.org/software/systemd/man/252/loginctl.html).

The runtime directory is user-private (`0700`) and contains transient sockets. With `pam_systemd`, `/run/user/$UID` is created for the user's login and removed after the final logout; its contents do not survive reboot. A new SSH login of the *same* UID may share that runtime directory, but this alone does not grant the SSH session seat ownership or make its environment equal to the graphical session's. `loginctl enable-linger` keeps a user manager running without a login; it does **not** create a graphical desktop or grant control of the seat. [XDG Base Directory Specification](https://specifications.freedesktop.org/basedir/0.8/); [`pam_systemd(8)`](https://www.freedesktop.org/software/systemd/man/251/pam_systemd.html); [`loginctl(1)`](https://www.freedesktop.org/software/systemd/man/252/loginctl.html).

Seat management is a different layer from display-client authorization. `logind` gives the active session controller access to seat devices and pauses that access when the session loses the foreground. `seatd`/`libseat` similarly mediate access to displays and input devices for compositor or X-server session management. An SSH process should connect as an authorized **client** of the already-running X server or Wayland compositor; it should not try to become a second seat controller or open `/dev/input` and DRM devices directly. [logind `TakeDevice` and `PauseDevice` contract](https://wiki.freedesktop.org/www/Software/systemd/logind/); [`seatd(1)`](https://man.archlinux.org/man/seatd.1.en).

## Discover and attach

Run read-only discovery over a plain SSH connection as the intended desktop user (or with enough privilege to inspect session metadata). Do not infer the graphical session from the SSH session's `$XDG_SESSION_ID`:

```sh
loginctl list-sessions --no-legend
loginctl show-session SESSION_ID \
  -p Name -p User -p Seat -p Remote -p Type -p Class -p Active -p State -p Display -p Leader
loginctl show-user USER -p RuntimePath -p Display -p Sessions
loginctl show-seat seat0 -p ActiveSession -p CanGraphical
```

`loginctl show-*` is the machine-readable interface; the properties above follow the [logind interface](https://wiki.freedesktop.org/www/Software/systemd/logind/) and [`loginctl(1)`](https://www.freedesktop.org/software/systemd/man/252/loginctl.html). `seat0` is a common default, not a required seat name. The implementation should check the actual seat and active session each time; session IDs, leaders, display numbers, and Wayland socket names are runtime values.

For Wayland, the client connects to `WAYLAND_DISPLAY`, usually a socket name relative to `XDG_RUNTIME_DIR`; the Wayland client API also allows an absolute socket path. The default `wayland-0` is only a fallback and cannot be assumed to identify the chosen compositor. For X11, `DISPLAY` identifies the X server and the client may also need `XAUTHORITY` pointing to the authority file containing its cookie. `xauth` defaults to `~/.Xauthority` if `XAUTHORITY` is absent, but a display manager can choose a different file, so neither path nor `:0` should be hard-coded. [Wayland client API](https://wayland.freedesktop.org/docs/html/apb.html); [Wayland server socket rules](https://wayland.freedesktop.org/docs/html/apc.html); [`xauth(1)`](https://man.openbsd.org/xauth.1).

The robust handoff is a small launcher or user service started *inside* the graphical login that records the selected session's environment (at least `DISPLAY`, `WAYLAND_DISPLAY`, `XAUTHORITY`, `XDG_RUNTIME_DIR`, `XDG_CURRENT_DESKTOP`, and session ID) in a private, per-login location or passes it to the worker directly. Another possible source is the user manager environment, **if** desktop startup imported the variables: `systemctl --user show-environment` inspects it, and desktop startup can call `dbus-update-activation-environment --systemd DISPLAY XAUTHORITY WAYLAND_DISPLAY XDG_CURRENT_DESKTOP`. That import is conditional and may be stale across desktop logout/login, so validate the selected socket/cookie against the active logind session before use. [D-Bus activation-environment manual](https://dbus.freedesktop.org/doc/dbus-update-activation-environment.1.html); [systemd `show-environment`/`import-environment` documentation](https://www.freedesktop.org/software/systemd/man/latest/systemctl.html). Reading `/proc/$PID/environ` of arbitrary processes is a brittle fallback: the chosen process may predate variables set during session startup, and access is subject to process permissions.

## Capture and input authorization

| Stack | Capture | Input/control | Authorization and unattended status |
| --- | --- | --- | --- |
| Native X11 session | X11 clients can obtain image data from a drawable with `XGetImage`; capture utilities may use X11 extensions. | XTEST can synthesize key, button, and pointer events when the server supports it. | A client must reach the local X server and have its X authority cookie (or another configured authorization). Once a valid cookie is available, normal X11 client operations can run without a per-capture chooser; protect the cookie as a broad desktop capability. [`XGetImage`](https://www.x.org/releases/current/doc/libX11/libX11/libX11.pdf), [XTEST](https://www.x.org/releases/X11R7.5/doc/man/man3/XTestFakeKeyEvent.3.html), [`xauth(1)`](https://man.openbsd.org/xauth.1). |
| Native Wayland session | The portable desktop-mediated path is ScreenCast portal selection, then a restricted PipeWire stream FD. | RemoteDesktop portal selects input devices and offers input event methods / EIS where supported. | The compositor and its portal backend mediate access. A successful Wayland socket connection alone does not grant arbitrary capture or synthetic input. Initial approval is normally a desktop dialog. Persistent permissions and token restoration are supported by the portal **interface**, but actual unattended restoration depends on the installed backend, its policy, an unchanged source/device, and non-revoked permission. [ScreenCast portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.ScreenCast.html), [RemoteDesktop portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.RemoteDesktop.html), [portal backend selection](https://flatpak.github.io/xdg-desktop-portal/docs/portals.conf.html). |

For a Wayland capture-only session, call `ScreenCast.CreateSession`, `SelectSources`, `Start`, then `OpenPipeWireRemote`. For input plus capture, use a `RemoteDesktop` session, select devices and screen sources, then start it; persistent *remote desktop* capture belongs to RemoteDesktop, not a separate persistent ScreenCast session. `persist_mode=2` requests permission until revoked, and the portal may return a `restore_token`. That token is **single use**: store the replacement token returned by every successful restored `Start`. If a source disappears, permissions are withdrawn, or restoration fails, the portal may present its chooser again. Treat absent renewal as an actionable `needs-local-consent` state, never as a reason to bypass the compositor. [ScreenCast portal methods and persistence](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.ScreenCast.html); [RemoteDesktop portal methods and persistence](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.RemoteDesktop.html).

PipeWire node IDs and D-Bus session handles are live-session resources, not durable identifiers. The ScreenCast interface warns that node IDs can be reused after destruction and recommends `pipewire-serial` for targeting when available. Portal stream FDs and local shared-memory/fd transport are host-local. The existing [ordinary-service forwarding research](../2026-09-13-tender-ordinary-service-forwarding-contracts.md) flags this as a separate capture/transfer boundary: forwarding an SSH command's bytes does not forward a portal's file descriptors or PipeWire transport. Capture must be performed by a host-local process and the resulting frames encoded/transferred explicitly. [ScreenCast stream contract](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.ScreenCast.html).

## Reboot and login lifecycle

At reboot, the graphical login, X server/compositor, runtime directory, authority cookie, portal sessions, and PipeWire streams all disappear. A persistent portal grant or saved restore token is a permission *request input* for a **new** session, not a surviving stream. On startup, wait for the intended `Class=user` graphical session to become active; rediscover its socket/display and authority material; start the host-local capture/control process; then reopen portal and PipeWire resources if using Wayland. Repeat after logout, compositor restart, seat switch, or portal revocation. [XDG runtime lifetime](https://specifications.freedesktop.org/basedir/0.8/); [`pam_systemd(8)`](https://www.freedesktop.org/software/systemd/man/251/pam_systemd.html); [logind active seat/session semantics](https://wiki.freedesktop.org/www/Software/systemd/logind/); [portal restoration semantics](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.RemoteDesktop.html).

If the machine stops at a greeter, there is no authenticated user desktop to attach to. An administrator may configure automatic login as a one-time machine policy; for GDM, Red Hat documents `[daemon] AutomaticLoginEnable=True` and `AutomaticLogin=USER` in `/etc/gdm/custom.conf`. Auto-login creates the user session after boot, but it also allows physical access to that account; this tradeoff needs explicit host-owner consent. A greeter-only or locked-desktop capture is a different product/security problem and should not be silently treated as a normal user session. [Red Hat GDM automatic-login procedure](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/8/html/using_the_desktop_environment_in_rhel_8/managing-user-sessions_using-the-desktop-environment-in-rhel-8); [logind session classes](https://wiki.freedesktop.org/www/Software/systemd/logind/).

If `paneer` uses SDDM (common with KDE), its documented `[Autologin]` `User=` and `Session=` settings select the account/session at startup. `Relogin=` additionally controls whether it logs that user in again after session exit; the default is false. These are distinct from restarting a capture process within an already-running session. [SDDM configuration manual](https://github.com/sddm/sddm/blob/develop/data/man/sddm.conf.rst.in).

### Current Porthole KDE adapter consequence

The current [KWin ScreenCast adapter](https://github.com/flotilla-org/porthole/blob/main/crates/porthole-adapter-kwin/src/screencast.rs) requests `persist_mode=2`, saves a portal-specific `restore_data` value under the user's cache directory, and retries without stale restore data. That may make **capture** restorable after process restart if the KWin portal accepts it; the saved value should be treated as a credential. This is an implementation-specific `restore_data` path, not proof that every backend implements the standard ScreenCast `restore_token` behavior described above. The current [RemoteDesktop input adapter](https://github.com/flotilla-org/porthole/blob/main/crates/porthole-adapter-kwin/src/remote_desktop.rs) requests `persist_mode=1` and does not visibly save or provide a restore token. Since mode 1 lasts only while the application runs, **input control currently should be expected to need another grant after adapter restart or reboot**. This is an inference from the source and [portal persistence contract](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.RemoteDesktop.html), to confirm on `paneer`. Porthole also requires its KWin control script enabled, so an authorized portal session alone is insufficient for the complete adapter path. [KWin adapter source](https://github.com/flotilla-org/porthole/blob/main/crates/porthole-adapter-kwin/src/lib.rs).

## Capability boundary and next validation

* **Unattended after a desktop is already logged in:** Session discovery and a same-UID X11 client with the current valid X authority can launch, capture, and drive the desktop. A Wayland portal session may be restorable unattended only where the chosen backend grants persistence and accepts restoration data. Current Porthole KDE capture has a restoration path, but its RemoteDesktop input path has no persistent grant across process restart. Both need a running, unlocked-enough desktop for the intended app and compositor policy.
* **One-time human/admin setup:** Install/select a display manager and desktop, create the intended local user, authorize SSH, decide whether auto-login is acceptable, arrange the graphical-session launcher/env handoff, and on Wayland approve portal capture/input and persistence when the backend asks. Configure the correct ScreenCast/RemoteDesktop portal backend for the desktop if absent. [Portal backend configuration](https://flatpak.github.io/xdg-desktop-portal/docs/portals.conf.html); [GDM auto-login procedure](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/8/html/using_the_desktop_environment_in_rhel_8/managing-user-sessions_using-the-desktop-environment-in-rhel-8).
* **Not guaranteed unattended:** First login from the greeter without auto-login, unlocking a locked desktop, granting a new/revoked portal permission, or capturing an arbitrary Wayland compositor that lacks suitable portal backend support. Treat those as explicit waiting/consent states, not SSH environment bugs. [logind class/active semantics](https://wiki.freedesktop.org/www/Software/systemd/logind/); [portal Start and restore behavior](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.RemoteDesktop.html).

Before choosing an implementation on `paneer`, record: `loginctl` session/seat properties; display manager and `XDG_SESSION_TYPE`; actual `DISPLAY`/`WAYLAND_DISPLAY`/`XAUTHORITY` from a process started in the desktop; existence of the user bus, PipeWire, `xdg-desktop-portal`, and selected portal backend; ScreenCast and RemoteDesktop interface versions; whether that backend issues/restores tokens across logout/reboot; and whether the intended app can run with a locked screen. These are empirical host checks, not facts established by the general protocol documentation.
