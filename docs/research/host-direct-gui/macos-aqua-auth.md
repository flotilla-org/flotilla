# macOS host-direct GUI session and authorization lifecycle

Research for [#1997](https://github.com/flotilla-org/flotilla/issues/1997), 2026-09-25. Scope: an agentless SSH connection to the Apple silicon `comte` or Intel `brie` host, where a crew must drive a native app and porthole must capture its screen. This is a mechanism report, not a verified host procedure: neither Mac was available for a live experiment. The operator-held `~/dev/rdg-dag/MACOS_REMOTE_AUTHORIZATION_RESEARCH.md` was unavailable to this crew and must be reconciled with these findings.

## Decision-relevant answer

An actual interactive user login is the prerequisite. Apple describes a `login/<asid>` domain as created by a GUI login and `gui/<uid>` as its UID-addressed form; `user/<uid>` can exist without that login. An Aqua agent is loaded only after GUI login, while a Background agent can run without one. A job bootstrapped into `gui/<uid>` therefore uses an **existing** GUI domain; it does not authenticate a user or create a desktop. `launchctl asuser` adopts a target user's bootstrap namespace and audit session, but does **not** change UID/GID or populate the user's environment. Run the GUI worker as the intended account, and prefer a user-owned Aqua LaunchAgent bootstrapped into the existing `gui/<uid>` domain to make its lifetime follow the GUI login. An SSH process alone is not proof of GUI access. [Apple `launchctl(1)` man page, as distributed with Xcode](https://keith.github.io/xcode-man-pages/launchctl.1.html), [Apple `launchd(8)` man page, as distributed with Xcode](https://keith.github.io/xcode-man-pages/launchd.8.html), [Apple DTS clarification](https://developer.apple.com/forums/thread/696859).

Apple's archived *Testing with Xcode* says SSH-driven `xcodebuild` GUI tests can work after a user is logged in at the host's GUI, and fail without the correct Aqua environment. That is evidence for this test path, **not a general guarantee** that arbitrary AppKit apps launched directly by SSH have every GUI service. Apple's older [TN2083](https://developer.apple.com/library/archive/technotes/tn2083/) warns about bootstrap-context differences; Apple DTS says its concepts remain useful although details drifted. The launch-agent path is the stronger default for crew and porthole, with direct SSH execution left as a host-specific test. [Apple, *Automating the Test Process*](https://developer.apple.com/library/archive/documentation/DeveloperTools/Conceptual/testing_with_xcode/chapters/08-automation.html), [Apple DTS](https://developer.apple.com/forums/thread/696859).

## Launch and inspection path

1. Have the intended ordinary user log in at the GUI. The `gui/<uid>` target must already exist. Do not treat `user/<uid>` or a successful SSH login as a substitute. `launchctl print` is useful for an operator's inspection, but Apple explicitly says its output format is **not an API**, so production code must not parse it. [Apple `launchctl(1)`](https://keith.github.io/xcode-man-pages/launchctl.1.html).
2. Install an Aqua LaunchAgent for the GUI worker, normally in that user's `~/Library/LaunchAgents/` or administrator-managed `/Library/LaunchAgents/`, with stable `Label`, `ProgramArguments`, and no `LimitLoadToSessionType=Background`. Apple DTS confirms unspecified session type defaults to Aqua; the agent then loads only in GUI contexts. An app-bundled agent registered through `SMAppService` can bootstrap immediately after user approval and on subsequent logins. [Apple DTS](https://developer.apple.com/forums/thread/696859), [Apple ServiceManagement `register()`](https://developer.apple.com/documentation/servicemanagement/smappservice/register%28%29), [Apple `launchctl(1)`](https://keith.github.io/xcode-man-pages/launchctl.1.html).
3. For an already logged-in account, the documented `launchctl` control shape is:

   ```sh
   uid=$(id -u GUI_ACCOUNT)
   /bin/launchctl print "gui/$uid"                       # diagnostic only
   /bin/launchctl bootstrap "gui/$uid" /absolute/path/to/agent.plist
   /bin/launchctl kickstart -p "gui/$uid/org.example.gui-worker"
   ```

   The `bootstrap`/`kickstart` syntax is documented; these are **illustrative commands**, not a tested recipe on `comte` or `brie`. Avoid re-bootstrapping an already loaded service. The actual label, file ownership, and privileges must be set for the chosen packaging. If using `launchctl asuser "$uid" command`, first switch credentials to that ordinary user when needed and set required environment explicitly; `asuser` alone does neither. Apple says launchd agents, rather than daemons with a changed UID, are the proper complete per-user identity for user interaction. [Apple `launchctl(1)`](https://keith.github.io/xcode-man-pages/launchctl.1.html), [Apple `launchd(8)`](https://keith.github.io/xcode-man-pages/launchd.8.html).
4. Gate GUI work on a real graphical session. Apple DTS suggests `SessionGetInfo` with `sessionHasGraphicAccess` as an explicit check, and cautions that a `CGWindowListCopyWindowInfo` heuristic is not guaranteed. Check the worker itself, then run a small real app-launch, input, and capture probe on each host; do not equate a domain existing, a window server connection, or one successful `xcodebuild` run with the complete porthole contract. [Apple DTS](https://developer.apple.com/forums/thread/696859), [Apple *Testing with Xcode*](https://developer.apple.com/library/archive/documentation/DeveloperTools/Conceptual/testing_with_xcode/chapters/08-automation.html).

## TCC grants and identity

The permission belongs to the **actual requesting app or binary**. Porthole and the app-driving worker may be different TCC clients; an SSH shell, terminal, helper, or parent/child chain can affect attribution, so inspect the prompt and the responsible process on each Mac rather than assuming a grant to one executable covers another. Apple's managed PPPC payload identifies a client by bundle ID or executable path **and code-signing requirement**, and suggests a TCC attribution log for diagnosing prompts. This favors a stable, signed helper identity and stable path; changing packaging, signature, or invoking process may require renewed approval. That last renewal statement is an inference from identity matching, not an Apple promise about every update. [Apple PPPC payload guide](https://support.apple.com/en-au/guide/deployment/dep38df53c2a/web).

| Capability | When needed | Grant or prompt | Unattended after setup? |
| --- | --- | --- | --- |
| Accessibility | Worker controls other apps through Accessibility APIs, including UI scripting. | User explicitly enables the requesting app in System Settings → Privacy & Security → Accessibility. On supported managed versions, a supervised, user-approved MDM PPPC payload can authorize identified apps; see version boundary below. | Yes while the grant and app identity remain valid, with GUI session present. [Apple user guide](https://support.apple.com/en-mn/guide/mac-help/mh43185/mac), [Apple PPPC guide](https://support.apple.com/en-au/guide/deployment/dep38df53c2a/web). |
| Screen & System Audio Recording / `ScreenCapture` | Porthole reads screen pixels through protected capture APIs. | User enables the capturing client in System Settings → Privacy & Security → Screen & System Audio Recording. Apple's ScreenCaptureKit sample prompts on first run and requires the app to restart after approval. PPPC can deny capture or permit a **standard user to make the setting**; Apple’s example still prompts and has that user click through. Treat PPPC as no silent screen-recording grant. | Yes while approved and an accessible GUI session remains; first grant is interactive. [Apple user guide](https://support.apple.com/en-eg/guide/mac-help/mchld6aa7d23/mac), [Apple sample](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos), [Apple PPPC guide](https://support.apple.com/en-au/guide/deployment/dep38df53c2a/web), [Apple PPPC example](https://support.apple.com/en-au/guide/deployment/dep9ddb7e0b5/1/web/1.0). |
| Automation / Apple Events | Only if the worker sends Apple Events to a target app, such as AppleScript `tell application`. It is separate from Accessibility. | macOS lists per-app Automation controls; Apple requires `NSAppleEventsUsageDescription` for an app using Apple-event APIs. Managed PPPC has an `AppleEvents` service for a specified sender and receiver. | Yes after the relevant sender → target approval, subject to identity and user choices. [Apple Privacy settings](https://support.apple.com/en-mt/guide/mac-help/mchl211c911f/mac), [Apple usage-description key](https://developer.apple.com/documentation/bundleresources/information-property-list/nsappleeventsusagedescription), [Apple PPPC guide](https://support.apple.com/en-au/guide/deployment/dep38df53c2a/web). |
| Input Monitoring / `ListenEvent` | Only if the worker **observes** keyboard/mouse input, such as an event tap; emitting clicks is a different capability. | User grants the requesting app under Privacy & Security → Input Monitoring. PPPC's Input devices entry and example show management/standard-user policy, but the example still leaves a user-facing permission step. Check the implementation's actual API before requesting it. | Yes if granted; do not request merely for output-only automation. [Apple Privacy settings](https://support.apple.com/en-mt/guide/mac-help/mchl211c911f/mac), [Apple PPPC guide](https://support.apple.com/en-au/guide/deployment/dep38df53c2a/web), [Apple PPPC example](https://support.apple.com/en-au/guide/deployment/dep9ddb7e0b5/1/web/1.0). |
| `PostEvent` | If the worker injects CoreGraphics `CGEvent`s into the system event stream. | Apple lists `Post Event` as a distinct PPPC service. Determine whether the intended driver uses this API and test the applicable authorization on both OS versions; Accessibility and Input Monitoring names alone do not prove it. | Conditional on tested API and grant. [Apple PPPC guide](https://support.apple.com/en-au/guide/deployment/dep38df53c2a/web). |

Apple's current deployment note adds a critical version boundary: the old `com.apple.TCC.configuration-profile-policy` **Accessibility grant** is deprecated as of macOS 26.2 and removed in macOS 27. The replacement `Privacy` key under `com.apple.configuration.app.settings` is for supervised devices and presents one consolidated **user consent** prompt at app first launch; it is not silent authorization. Apple's WWDC26 page marks its macOS 27 material as prerelease, so recheck at the final release. Record `sw_vers` on `comte` and `brie` before selecting a managed path. [Apple WWDC26 deployment update](https://support.apple.com/en-au/guide/deployment/depd567c9ffa/web).

## Login, lock, restart, renewal

| State or transition | What SSH can do | GUI automation status / human action |
| --- | --- | --- |
| User has logged in, desktop active, TCC already approved | Start or signal a correctly placed Aqua agent; send work to it. | **Unattended-capable** for the tested APIs, app, and capture path. GUI login is already supplied. [Apple `launchctl(1)`](https://keith.github.io/xcode-man-pages/launchctl.1.html), [Apple *Testing with Xcode*](https://developer.apple.com/library/archive/documentation/DeveloperTools/Conceptual/testing_with_xcode/chapters/08-automation.html). |
| SSH only; no GUI login yet | Run background commands and query user domain. | **Human GUI login required** before ordinary Aqua app driving. `bootstrap gui/<uid>` and `asuser` do not manufacture it. [Apple `launchctl(1)`](https://keith.github.io/xcode-man-pages/launchctl.1.html), [Apple DTS](https://developer.apple.com/forums/thread/696859). |
| GUI session locked or switched away | SSH and background work may continue. | **Pause app driving** until the intended user's desktop is unlocked and foreground. Screen sharing or recording may continue while locked—Apple documents a lock-screen observation reminder—but that does not establish that porthole can capture the target app's pixels or control it then. Test the exact capture path on each host. Lock, logout, and user switching may still require a password. Do not claim ordinary user TCC approval grants control of loginwindow or the lock screen. [Apple automatic-login guide](https://support.apple.com/en-ca/102316), [Apple lock-screen screen-observation guide](https://support.apple.com/en-us/120315). |
| Reboot with FileVault on | SSH service availability before disk unlock is host/configuration dependent; do not count on it for renewal. | FileVault disables automatic login. A FileVault-authorized human must unlock/login for a new Aqua session; `comte` already has this post-reboot human step. Then the Aqua agent can reload on login, and the worker can re-check TCC. [Apple automatic-login guide](https://support.apple.com/en-ca/102316), [Apple `launchctl(1)`](https://keith.github.io/xcode-man-pages/launchctl.1.html). |
| Reboot with FileVault off and automatic login deliberately enabled | After startup, SSH can reach the machine once network/remote login are ready. | Automatic login can create the user's GUI session without a person after each reboot; it is a **security-policy choice and one-time human setup**, and organizational profiles or Apple Account password settings can prohibit it. Locking or logging out can still demand a password. [Apple automatic-login guide](https://support.apple.com/en-ca/102316). |
| Existing TCC grant, ordinary reboot or user relogin | Restart the same approved helper in the renewed GUI session and check permissions. | A grant is intended to be retained as a user privacy setting; Apple documents reviewing/toggling it and an initial ScreenCaptureKit app restart, but does not promise uninterrupted approval across re-signing, bundle/path changes, OS upgrades, policy changes, or device replacement. Treat each as a renewal trigger and verify. [Apple Accessibility guide](https://support.apple.com/en-mn/guide/mac-help/mh43185/mac), [Apple screen recording guide](https://support.apple.com/en-eg/guide/mac-help/mchld6aa7d23/mac), [Apple ScreenCaptureKit sample](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos), [Apple PPPC guide](https://support.apple.com/en-au/guide/deployment/dep38df53c2a/web). |

Automatic login is not a recommendation to turn off FileVault. Apple warns it lets anyone access the Mac after restart and specifically notes FileVault prevents it. The design decision is whether these hosts retain a human post-reboot login gate or accept the risk and policies of automatic login. [Apple automatic-login guide](https://support.apple.com/en-ca/102316), [Apple login-window guide](https://support.apple.com/en-om/guide/mac-help/mchlp1158/mac).

## Host checks and unresolved points

1. Record macOS version, account UID, FileVault and auto-login policy on `comte` and `brie`; inspect whether `gui/<uid>` exists **after** actual login. Compare `launchctl print user/<uid>` and `launchctl print gui/<uid>` manually; do not parse output as a machine contract. [Apple `launchctl(1)`](https://keith.github.io/xcode-man-pages/launchctl.1.html).
2. Prove the selected worker packaging with one benign native app in the existing GUI session, and confirm `sessionHasGraphicAccess` inside that worker. Test the direct-SSH path only as a comparison. The archive's SSH/Xcode claim and TN2083's broader bootstrap caution should be reconciled empirically on each current OS version. [Apple DTS](https://developer.apple.com/forums/thread/696859), [Apple *Testing with Xcode*](https://developer.apple.com/library/archive/documentation/DeveloperTools/Conceptual/testing_with_xcode/chapters/08-automation.html), [Apple TN2083](https://developer.apple.com/library/archive/technotes/tn2083/).
3. Inventory the exact APIs used by the driver and porthole, then trigger and record each TCC prompt's attributed binary, bundle ID, path, code requirement, and target app for Apple Events. Apple's TCC log command is `log stream --debug --predicate 'subsystem == "com.apple.TCC" AND eventMessage BEGINSWITH "AttributionChain"'`; do not include unrelated sensitive log data in reports. [Apple PPPC guide](https://support.apple.com/en-au/guide/deployment/dep38df53c2a/web).
4. Probe active desktop, locked desktop, fast-user-switched desktop, logout, and reboot separately. In particular, determine whether porthole captures target-app pixels, lock-window pixels, or no useful frames while locked. Apple confirms that some screen sharing or recording can continue during lock; the operational default is to pause app control and treat target-app capture as unverified until the authorized user returns. [Apple lock-screen screen-observation guide](https://support.apple.com/en-us/120315), [Apple automatic-login guide](https://support.apple.com/en-ca/102316).
5. Reconcile the unavailable operator-held research before final design choice, especially any claim that SSH/`asuser` alone creates Aqua, TCC can be silently granted, or FileVault and automatic login coexist. The Apple sources above would conflict with those claims.
