# SSH-only hosts and host-direct GUI crew: current state

Research for [#2000](https://github.com/flotilla-org/flotilla/issues/2000), at commit `2a64996cc6e9daa001f497fecf8a2a277e855d84` (2026-09-25). “Host-direct” here means a trusted, non-container vessel using a host worktree and terminal pool. The code does **not** yet make an SSH-only machine a Plane B placement target.

## Two existing SSH paths, with different purposes

1. `hosts.toml` has `RemoteHostConfig` (`hostname`, expected daemon host name/node ID, optional user and SSH multiplex setting). `ssh_destination` formats `user@hostname`; the fleet replica path runs `ssh -T ... flotilla --json replica-snapshot` and checks the expected daemon identity. This is a way to **read a remote daemon's snapshot**, not a definition of an agentless Plane B Host. Sources: [config](../../../crates/flotilla-core/src/config.rs#L226-L295), [SSH snapshot command](../../../crates/flotilla-core/src/in_process.rs#L859-L907).
2. `daemon.toml` has static `environments` with `hostname`, optional `display_name`, and `flotilla_command`. At startup, `register_static_ssh_direct_environment` constructs an `SshCommandRunner`, preflights `true` in a five-second timeout, reads remote `env`, resolves environment/host IDs, runs host detectors through SSH, then registers a **direct environment in the in-process EnvironmentManager**. Failure logs a warning and startup continues. The SSH runner uses batch-mode `ssh -T`, shell-quoted commands, and remote file helpers; it is explicitly a direct execution runner rather than daemon transport. `flotilla_command` is declared but not consumed by that registration path. Sources: [config](../../../crates/flotilla-core/src/config.rs#L297-L315), [static config](../../../crates/flotilla-core/src/config.rs#L394-L402), [registration](../../../crates/flotilla-core/src/in_process.rs#L500-L550), [runner](../../../crates/flotilla-core/src/providers/ssh_runner.rs#L37-L151).

`resolve_or_create_remote_host_id` obtains a remote state directory from `XDG_STATE_HOME` or `HOME`, returns `None` if neither exists, then reads or atomically ensures its `host-id` file through the remote runner. That ID is an execution-environment identity, **not** by itself a `Host` resource. The EnvironmentManager stores the runner, discovery bag and optional host ID; visible direct environments can be shown as running, while host summary enumeration covers provisioned environments. Sources: [host identity](../../../crates/flotilla-core/src/host_identity.rs#L410-L475), [manager registration](../../../crates/flotilla-core/src/environment_manager.rs#L109-L133), [environment visibility](../../../crates/flotilla-core/src/environment_manager.rs#L214-L242).

The similarly named `EnvironmentAssertion::RemoteHost` means a **Git remote repository host** (GitHub/GitLab platform, owner, repository and remote name), produced from Git remotes. It is not an SSH machine or a `Host` resource. Sources: [assertion type](../../../crates/flotilla-core/src/providers/discovery/mod.rs#L56-L70), [Git detector](../../../crates/flotilla-core/src/providers/discovery/detectors/git.rs#L112-L167).

## What host-direct placement and provisioning provide today

At daemon startup, the **local** provisioning profile is built from the local host ID, HOME, local provider registry, terminal pools and adapters. Startup registers its local `Host`, `host-direct-<host-id>` `Environment`, discovered clones and `host-direct-<host-id>` `PlacementPolicy`. The policy specifies a pool, `host_ref`, and Worktree checkout. There is no corresponding resource-registration loop for static SSH direct environments. Sources: [local profile and registration](../../../crates/flotilla-daemon/src/runtime.rs#L1113-L1154), [environment](../../../crates/flotilla-daemon/src/runtime.rs#L1250-L1274), [policy](../../../crates/flotilla-daemon/src/runtime.rs#L1352-L1367), [policy schema](../../../crates/flotilla-resources/src/placement_policy.rs#L58-L86).

Convoy admission enumerates local and replicated policies. It rejects a contained workflow on host-direct, checks required agent adapters and credentials, resolves the policy's `host_ref` against actual `Host` resources, and orders viable policies by priority, local host, then host-direct. Host-direct adapter admission requires a ready `Host` status with a fresh heartbeat and advertised adapters; credentials also use host status. Remote placement checks an observed admission free-space floor. Sources: [selection](../../../crates/flotilla-core/src/in_process.rs#L1233-L1403), [adapter check](../../../crates/flotilla-core/src/in_process.rs#L4550-L4582), [credential check](../../../crates/flotilla-core/src/in_process.rs#L4380-L4435), [capacity](../../../crates/flotilla-core/src/in_process.rs#L5874-L5911), [Host status](../../../crates/flotilla-resources/src/host.rs#L44-L107).

The chosen host's daemon actuates its vessel; a daemon whose local host ID differs from the placement decision returns without provisioning it. The host-direct vessel uses the host-local ready environment, creates/awaits a shared clone and worktree checkout, then creates a `TerminalSession` with the selected pool and workspace cwd. Agent sessions receive a rendered brief, credential references/scopes and crew environment variables; the terminal runtime resolves the environment's provider registry and runner. Sources: [actuator check](../../../crates/flotilla-controllers/src/reconcilers/vessel.rs#L270-L304), [host-direct environment and terminal creation](../../../crates/flotilla-controllers/src/reconcilers/vessel.rs#L697-L1024), [terminal runtime](../../../crates/flotilla-daemon/src/runtime.rs#L3533-L3615). The host-direct environment controller marks the local environment ready without container provisioning; it skips foreign hosts. Sources: [environment reconciler](../../../crates/flotilla-controllers/src/reconcilers/environment.rs#L33-L124). A two-daemon test reaches Running with remote host-direct placement across replicated stores and confirms the checkout/environment/actuator vessel live on the placement daemon. Source: [integration test](../../../crates/flotilla-daemon/src/runtime.rs#L7140-L7311).

## Gap to “place a host-direct GUI crew on beaufort/comte/brie over SSH”

**Current result:** an SSH-only host can be configured as a direct command/discovery environment on an existing daemon. It is not automatically a Plane B `Host`, ready `Environment`, or `PlacementPolicy`; no daemon exists on it to run the host-local vessel, checkout, terminal and presentation reconcilers. Merely adding `host_ref = "beaufort"` to a policy fails host resolution unless a Host resource is separately created, and a manually created Host still lacks the heartbeat/status, adapter and capacity facts required by admission. Manually fabricating those facts would not provide an actuator. Sources: [SSH registration](../../../crates/flotilla-core/src/in_process.rs#L500-L550), [local-only resource registration](../../../crates/flotilla-daemon/src/runtime.rs#L1113-L1154), [host resolution](../../../crates/flotilla-core/src/in_process.rs#L1233-L1280), [actuator check](../../../crates/flotilla-controllers/src/reconcilers/vessel.rs#L270-L304).

**Needed Plane B work (inference from those code paths):** define an agentless Host flavor with SSH endpoint and stable identity; publish probe-based health/capabilities/free-space and credential facts without claiming a daemon heartbeat; generate or configure a host-direct Environment and PlacementPolicy for it; make admission understand those facts; assign an owning daemon to reconcile its vessel and host-local descendants using the SSH runner; and make terminal/presentation session creation, observation, attach and cleanup work across that boundary. GUI-specific capability/availability (interactive desktop session, display access and recording/control, if required) must be checked separately: current policy only expresses pool, host and checkout, and the [requirements-first placement ADR](../../../docs/adr/0007-requirements-first-placement.md#L5-L25) names `gui: recordable` as prospective capability vocabulary, not current policy behavior. This report does not claim SSH command execution proves GUI session support.

**Unattended-capable after one-time setup:** if SSH keys/host trust, a writable remote HOME/state directory, required binaries and agent credentials are already installed, the configured direct runner can preflight, discover and execute commands without a remote daemon or an interactive prompt. Existing daemon-to-daemon host-direct placement can provision worktrees and crew sessions unattended once the target daemon, its resource store/replication and providers are running. Sources: [SSH runner](../../../crates/flotilla-core/src/providers/ssh_runner.rs#L37-L151), [registration](../../../crates/flotilla-core/src/in_process.rs#L500-L550), [two-daemon test](../../../crates/flotilla-daemon/src/runtime.rs#L7140-L7311).

**One-time human/operator setup still needed today:** establish SSH access and host keys; install/configure the remote tools, terminal pool, agent adapter, credentials and any GUI desktop access; configure `daemon.toml` static environment for command use. For actual Plane B placement today, run/configure a Flotilla daemon on the target so it advertises a Host, policy and environment. The latter is not available on the ssh-only machines assumed by the question, so placing such a GUI crew is **not currently an unattended operation**. These setup categories are operational implications of the code, not proof that all named machines have or lack particular software.

[#1186](https://github.com/flotilla-org/flotilla/issues/1186) is **open** (checked with `gh api repos/flotilla-org/flotilla/issues/1186` on 2026-09-25). Its body explicitly calls for an agentless Host with probe-based health, SSH execution and placement, and leaves remote actuation/transport open. The static SSH runner answers only part of that issue's execution question. This is part of [#1996](https://github.com/flotilla-org/flotilla/issues/1996), not evidence that #1186 has been implemented.
