# Why Plane-A rebuilt development images

## Finding

The demonstrated cause was **a new UUID image tag on every Dockerfile-backed ensure**. The [initial provider](https://github.com/flotilla-org/flotilla/commit/a19bc790908f5f9cca118cb6226bf23ce4abeef4) unconditionally ran `docker build -t flotilla-env-{uuid}`. Once [environment checkout provisioning](https://github.com/flotilla-org/flotilla/commit/5e5d30a176a8f397d421c29a733f2f4e28c6cb87) called it, each new environment checkout requested another build even if the recipe was unchanged. [PR #572](https://github.com/flotilla-org/flotilla/pull/572) explicitly identified that waste and [replaced UUID tags](https://github.com/flotilla-org/flotilla/commit/9bd055a71acb02fecc29c317af72887977bf99f0) with a deterministic SHA-256 tag and local `docker image inspect` on April 6. This proves the mechanism from the initial implementation through that fix; the repository contains no build-count telemetry establishing how often operators actually invoked it.

## What was built and when

- The repo's [environment spec](https://github.com/flotilla-org/flotilla/blob/87f03e9d11e34293fa25902d23b03cd6bc5402c0/.flotilla/environment.yaml) points to the relative `.flotilla/Dockerfile.dev-env`. The Dockerfile began as a small development image in [PR #507](https://github.com/flotilla-org/flotilla/pull/507), then became an omnibus Rust and agent-CLI image in [PR #561](https://github.com/flotilla-org/flotilla/pull/561) (restored to main by [commit ea237de](https://github.com/flotilla-org/flotilla/commit/ea237de21e207929d277ef7abb060bba5e9812bc)). This edit preceded the hash implementation; its git history does not show ongoing per-branch edits.
- The [checkout planner](https://github.com/flotilla-org/flotilla/blob/87f03e9d11e34293fa25902d23b03cd6bc5402c0/crates/flotilla-core/src/executor.rs#L199-L219) selects the new-environment plan only for `NewEnvironment`; the [plan](https://github.com/flotilla-org/flotilla/blob/87f03e9d11e34293fa25902d23b03cd6bc5402c0/crates/flotilla-core/src/executor.rs#L473-L511) reads the spec and creates an environment before creating the checkout. The [executor](https://github.com/flotilla-org/flotilla/blob/87f03e9d11e34293fa25902d23b03cd6bc5402c0/crates/flotilla-core/src/executor.rs#L1200-L1227) reads `.flotilla/environment.yaml` from `HEAD` and calls `ensure_image` once in `CreateEnvironment`. Reusing an existing environment follows a [different plan](https://github.com/flotilla-org/flotilla/blob/87f03e9d11e34293fa25902d23b03cd6bc5402c0/crates/flotilla-core/src/executor.rs#L543-L575) without this call. Normal host checkouts do not enter the new-environment plan.
- Since PR #572, the [provider](https://github.com/flotilla-org/flotilla/blob/87f03e9d11e34293fa25902d23b03cd6bc5402c0/crates/flotilla-core/src/providers/environment/docker.rs#L43-L68) hashes version `v1`, the **spec path string**, and Dockerfile bytes. It inspects that tag in the target host's local Docker daemon, building only on a miss. A successful inspect skips the build, as the [test](https://github.com/flotilla-org/flotilla/blob/87f03e9d11e34293fa25902d23b03cd6bc5402c0/crates/flotilla-core/src/providers/environment/tests.rs#L232-L247) confirms.

## Suspects after the fix

| Suspect | Evidence and verdict |
| --- | --- |
| Branch or checkout differences | **Possible cache miss, not a demonstrated recurring cause.** The provider reads Dockerfile bytes from the executing repository root. If source worktrees contain different Dockerfile bytes, they get different tags; the target branch checkout is created *after* the image ensure and cannot change that ensure's inputs. The checked-in file has an initial version and one omnibus revision in git history, not evidence of constant edits. The spec comes from `HEAD` while the Dockerfile bytes come from the filesystem, so an uncommitted Dockerfile edit can also change the tag. |
| Spec path varying across worktrees | **Not for this repo's checked-in spec.** The hash uses the literal relative `.flotilla/Dockerfile.dev-env`, not its worktree-resolved absolute path. An absolute or differently spelled spec path would produce another tag, but the checked-in spec does not use one. |
| Eviction or pruning | **Possible local cache miss, unproven here.** `docker image inspect` failure is treated as absence, and the provider then builds. [scripts/prune-target.sh](https://github.com/flotilla-org/flotilla/blob/87f03e9d11e34293fa25902d23b03cd6bc5402c0/scripts/prune-target.sh) caps a checkout's Cargo `target`, not Docker images. Repository search found no Docker-prune invocation; host-local pruning or eviction cannot be ruled out without host records. |
| Builds on different hosts | **Yes, structurally.** The environment steps execute on the target host and `docker image inspect` consults only that host's daemon. The computed tag is portable for identical inputs but the provider neither pulls nor publishes Dockerfile images, so the first use on each host builds locally. |
| Unpinned installs | **Build cost and reproducibility risk, not a tag-change trigger.** The [omnibus Dockerfile](https://github.com/flotilla-org/flotilla/blob/87f03e9d11e34293fa25902d23b03cd6bc5402c0/.flotilla/Dockerfile.dev-env) has unpinned Claude/Cursor installers and moving package/base-image sources. External updates alone do not change the hash or cause a rebuild; if a build is triggered for another reason, it can resolve different versions under the same tag. |

The later [#1088 discussion](https://github.com/flotilla-org/flotilla/issues/1088) records the owner's recollection of repeated builds and preference for a curated image. [#1102](https://github.com/flotilla-org/flotilla/issues/1102) describes the March 30 `flotilla-dev-env:latest` as a 4.35 GB local-only image and motivates layered, published images for Plane B. That tag does not match either `ensure_image` naming scheme and should not be counted as an `ensure_image` build. These records corroborate the operational pain, but do not provide a build log or identify any additional recurring post-April trigger. The [Plane-B pull failure](https://github.com/flotilla-org/flotilla/issues/1087) concerns a separate placement path and does not explain Plane-A rebuilds.

## Design rule for #2267

An image's identity must be stable for the same **resolved build inputs**, independent of checkout, branch name, random ID, and build host, with deliberate versioning of any inputs that affect the result. Resolve moving dependencies to explicit versions or digests, include the complete build context and chosen architecture where they affect the output, and make the resulting identity retrievable or reusable across hosts. A new environment dispatch may then ensure that identity; it should not invent a new image identity merely because it ran again. The old UUID behavior violates the first rule, while the current Dockerfile-only fingerprint is too narrow to guarantee the second. This is a design inference from the [old and new provider implementations](https://github.com/flotilla-org/flotilla/pull/572/files) and [#2267's destination](https://github.com/flotilla-org/flotilla/issues/2267), not evidence of another observed rebuild cause.
