# Forge observation is owned once per source

Every host independently polling every Project multiplies traffic against the same forge identity. Forge observation is now source-scoped: the origin of the earliest Project declaration binding the source is preferred, with origin ID breaking ties. This is the Project's declaration home, recovered from original stored sources rather than the merged Definitions view. Projects sharing a source share one observer. PR observation uses Repository forge identity even when issue bindings exclude that forge.

A preferred owner with unknown health retains ownership for a three-minute startup grace from its Host declaration, or its Project declaration when no Host exists. After that grace, unknown health is unready; an owner that never reports cannot block polling forever. Positive unready evidence or a heartbeat older than three minutes permits the first ready daemon origin in sorted order to observe. Agentless Hosts never qualify. No ready daemon means no polling. Elections rely on the replicated membership/health view; they are not a consensus lease and do not provide fencing across arbitrary network partitions. A stricter partition guarantee requires a fleet lease authority, rather than independent writes to replicated stores. Dispatch reconciliation stays on the Project declaration home, independently of observation failover; moving it to the fleet admission decider remains #2785's responsibility.

Source-addressed adapters publish replicated ForgeRead demand and successful results. Nonowners publish demand and read those results, never calling the forge. The owner services demand on the existing board observation cadence. Results are cached for one minute, coalesced by natural request identity and shared local request locks, and retain the last successful value and its observation time through errors. Only completed observations are stored: cancelled or handed-off loads leave no transient pending claim. Final status publication retries resource-version conflicts caused by demand touches. Observation timestamps are taken at completion. Reported retry deadlines suppress refresh. Background servicing does not renew demand, and idle local requests expire after an hour; replication carries their tombstones. Bound Issue and ChangeRequest observation uses the same election before acquiring its existing record authority and publishes through its existing observation replication class. Interactive forge mutations and admission reads remain explicit operations. Checkout-branch admission uses a fresh targeted lookup rather than authorizing creation from a cached absence. Replicated read status distinguishes a missing result from a successful null result, so optional branch lookups remain usable after storage and replication.

The alternative of merely guarding each timer would leave interactive cache misses, per-subject observers, and shared Projects able to multiply reads. A replicated demand/result boundary covers those callers together without transferring credentials or coupling nonowners to a live RPC at read time. Hourly host gh identity accounting records REST cost and returned GraphQL cost, explicitly separates CLI calls without reported GraphQL cost, and publishes reset-based backoff. Host heartbeats replicate these diagnostics for fleet health.

GitHub's timed board path validates REST issues and PR collections ordered by update time. A durable cursor stops paging at the first older item, preserving the inclusive timestamp boundary; revision keys select targeted detail reads. Collection URIs remain stable so ETag validation survives a quiet interval (changing `since` on every poll would invalidate query-specific validators). PRs follow this updated-cursor rule. Issues first validate a stable conditional first-page probe; when it changes, they fetch a delta with `since` derived from the durable cursor. The delta overlaps one second because GitHub defines `since` as strictly after; revision deduplication preserves the inclusive timestamp boundary. Quiet probes reuse their request-specific ETags without moving the URI. Native fields absent from REST use targeted `gh issue view`/`gh pr view`, never whole-board GraphQL scans. PR check/status responses participate in the detail revision because CI can advance without a PR update. Bound PR observation likewise validates REST item/check revisions before its existing targeted GraphQL batch. Mission fields, dependency lists and closing-PR states use conditional REST reads.

ETags and their response bodies, collection cursors, and revision-keyed detail values persist beneath the daemon state directory's `forge-cache/github` subtree, using private atomic files. Providers rediscovered between polls recover this state. A failed detail pass does not advance its collection cursor; the next attempt can replay the conditionally cached collection body. These are disposable observation caches, not authored resources: removing the subtree before restarting the owning daemon explicitly requests a full resynchronization. The initial pass still costs collection pages plus targeted details. Readiness failover transfers replicated observations and demand; a new observer without a local conditional cache performs an initial synchronization. Webhook delivery is an acceleration hint and is not required for polling correctness.

The fleet is one trust domain. Joining hosts and resource writers are trusted with all forge data readable by the fleet's configured identities, including replicated issue/PR contents and query parameters. A demand asks the elected observer to use that identity; it is not a per-host GitHub authorization boundary. Do not join an untrusted host to a fleet with privileged forge credentials. Separate fleets are required for separate authorization domains.

Host clocks are assumed synchronized. Heartbeat expiry, unknown-owner grace, observation freshness and latest-attempt ordering use UTC across origins; large clock skew can delay failover or make an old observation appear newest. Authority ID breaks equal-timestamp ties consistently for reads and board metadata, but does not cure skew. A per-authority generation or fenced lease would require a separate ordering/authority protocol. Election reads current replicated state before and after each load, rather than caching a stale owner across a health transition. Declaration homes are recovered in one replica-source snapshot per election to avoid repeated per-binding Project listings.
